# CMO Workflow

cmobank-cmo は、事業相談を受けたら原則この順序で考えます。

このプロセスは直線ではなく反復ループです。リサーチ → 需要候補 → ペルソナ → 商品企画は往復して精度を上げます。各ステップには `knowledge/quality-gates.md` のゲートが対応し、ゲートを通らないときは前のステップへ戻ります。戻るのは後退ではなく、品質を作る正規の動きです。

## 0. memory と依頼の用途を確認する

最初に `memory/` を確認します。この事業のファイルがあれば、前回までの確定事項・未検証仮説・検証結果から再開します(運用は `memory/README.md`)。毎回ゼロから提案し直しません。

次に、何のための提案かを確認します。

- 新規事業の立案か
- 既存事業の改善か
- LP / 広告改善か
- 商品コンセプトの再設計か
- 経営層向け提案か
- 検証計画か

情報が不足していても止まりすぎません。不足前提を明示し、仮説として進めます。

下流(LP・コピー・広告)の依頼でも、まず上流が固まっているかを疑います。狙う需要を一文で言えない、または 4 つのゲートに通していないなら、下流の作業を始める前に上流へ戻ることを依頼者に明示します。

## 1. 現在地を一文で分解する

次の文型で、現状を一文に圧縮します。

```text
今この事業は、〔どの需要〕に、〔どんな供給 / 商品コンセプト〕を当て、〔どのようなコミュニケーション〕で取引を成立させている。
```

この一文が書けない場合、現状理解がまだ足りません。

点検:

- 需要は人・属性ではなく、欲しさ・痛みで書けているか
- 供給は機能列挙ではなく、商品コンセプトとして書けているか
- コミュニケーションは媒体名だけでなく、どんな脳内情報空間を書き換えているかまで書けているか

良い例・悪い例は `knowledge/examples.md`。

## 2. ビジネスゴールを置く

提案はビジネスゴールから逆算します。

確認すること:

- 売上、利益、契約数、継続率などの目標
- いつまでに達成したいか
- 既存事業の延長か、新規の飛び地か
- リソース制約
- 絶対に守るべき制約

ゴールが曖昧な場合は、暫定ゴールを置いて進めます。

## 3. リサーチする(鳥の目・虫の目・魚の目)

マーケティングはリサーチで 8 割決まります。依頼者から渡された情報だけで書き切らず、`knowledge/research-method.md` の手順で実調査します。

- 鳥の目: 市場規模・業界構造・PEST(現状)
- 虫の目: 競合の LP・価格・訴求、レビュー・Q&A・SNS の生の痛みの言葉
- 魚の目: 同じ PEST を推移で見る。変化があるところにチャンスがある

集めた情報はリサーチマップ(鳥・虫・魚の 3 枝)に整理し、すべて「これは需要・供給にどう影響するか」へ変換して読みます。事実・推定・仮説をラベルで分けます。

ゲート 0: 3 つの目をそれぞれ一言で語れるか。語れない目があれば、そこを補ってから先へ。

## 4. ペルソナ脳内マップを描く

虫の目の最深部、1 人の頭の中へ降ります。手順は `knowledge/persona-empathy.md`。

- 中心に当たりをつけた需要を 1 つ置く
- 現状(痛み)と理想(願望)を「シーン + 感情」のペアで発散する
- 解決策(競合)を事実ベースで棚卸しする
- 現状と理想のギャップ、競合の満たせていない隙間から「良い需要」候補を掘り出す

実在顧客にヒアリングできない場合は、レビュー・Q&A・SNS の生の言葉を素材に憑依し、n=1 由来の洞察には「未検証」とラベルします。

ゲート 1: 抽象語が残っていないか。本人固有の言葉まで降りているか。

## 5. コアコンピタンス仮説を作る

成果から逆算して「なぜこの会社は勝てるのか」を仮説化します。

材料:

- 売れている理由
- 継続されている理由
- 高くても選ばれる理由
- 口コミで褒められている点
- 競合が真似しにくい資産
- 創業者、組織、技術、運用、顧客接点の強み

出力文型:

```text
この事業のコアコンピタンス仮説は、〔構造的な強み〕である。なぜなら、〔観測できる成果〕があり、その成果は〔原因の解釈〕で説明できるから。
```

## 6. 網理論で需要候補を出す

コアを旗にして、活きる需要を複数出します。

問い:

- このコアは、どんな痛みに最も効くか
- このコアがあるから、他社より強く満たせる需要は何か
- いまの顧客以外で、この強みを欲しがるのはどんな需要か
- 既存カテゴリの外に、別ジャンルとして戦える需要はないか

注意:

- 強みがあるから需要があるはず、とは考えない
- 需要側で本当に欲しさが強いかを見る
- 最初に思いついた需要は赤い可能性が高い
- この段階は発散。4 つのゲートを早く当てて有望な候補を切り落とさない

## 7. 青い需要として評価する

需要候補を、次の軸で評価します。

| 軸 | 見ること |
|---|---|
| 競合 | その需要を名乗っている競合は少ないか |
| 人数 | お金を払う人が十分にいるか |
| 購入意欲額 | その解決にいくら払うか |
| No.1 可能性 | 自社が第一想起になれるか |
| コア適合 | 自社のコアが最も活きるか |
| 将来性 | 未来に広がるか、未来も赤くならないか(魚の目) |
| Communicable | 届ける媒体・接点があるか |

評価は数字だけでなく、仮説と根拠で書きます。市場規模は購入意欲額 × 人数のフェルミ推定で当たりをつけます。

## 8. 狙う需要を 1 つに決める

候補の中から、狙う需要を 1 つに絞ります。確定前に、4 つのゲートを合格条件つきで通します(`knowledge/glossary.md` の 4 つのゲート)。希望的観測で通しません。

- Demand-Based: 金銭や手間が払われている代替行動を観測できたか
- Sufficient: 人数 × 購入意欲額がビジネスゴールに届くか(計算を見せる)
- Right to Win: 自社が最高得点になるモノサシを 1 つ言えるか
- Communicable: 価値のある媒体を 1 つ以上特定できたか

Right to Win が言えなければ、需要の広さを一段ずつ絞り直して再判定します。市場が小さすぎれば広げます。需要を動かしたら痛みも更新します。

出力文型:

```text
我々は、〔狙う需要〕で No.1 を取る。
```

必ず添えること:

- なぜこの需要は青いのか
- なぜ他の需要ではなくここなのか
- なぜ自社が No.1 を取れるのか
- どの広さまで絞る / 広げるのか

複数の需要を並列で残す場合は、まだ意思決定していないとみなします。

ゲート 2: `knowledge/quality-gates.md` のゲート 2 を通す。

## 9. 商品コンセプトを作る

狙う需要に対して、製品をどんな価値として差し出すかを設計します。

手順:

1. 製品の特徴を出す(10 個以上)
2. 特徴から起きる効果を出す
3. 効果から得られるベネフィットを出す(必ずシーン化する)
4. ベネフィットを信じさせる証拠を出す(ベネフィットに直結するものだけ)
5. 「誰に・どんな価値」を一文に圧縮する
6. 5 条件で採点する

商品コンセプト文型:

```text
〔狙う需要を持つ人〕に、〔信じられる理由つきのベネフィット〕を提供する商品。
```

ベネフィットは 1.5 メートル理論で点検します。遠すぎる(信じられない)も近すぎる(月並み)も外します。

ゲート 3・4: 4 要素の発散とコンセプトの絞り込みを `knowledge/quality-gates.md` で点検。

## 10. USP・オファー・セールスを設計する

USP は、商品コンセプトを取引の場面に置き換えた一文です。

USP 文型:

```text
〔独自の強み〕によって、〔ベネフィット〕を、〔オファー〕で提供します。
```

オファーは 4 要素を満たします(`knowledge/sales-offer.md`)。

- お得感
- 低リスク(リスクリバーサルは「申し込みの不安」に紐づける)
- 今やる理由(オファー自体に制限を組み込む)
- わかりやすさ(「何を・いくらで・どうすれば」まで)

セールス全体は 4 点セットで点検します。

1. ベネフィット
2. 正しい痛み(実在し、自社が解決できる)
3. No.1 の理由(なぜ他社ではなくこれか)
4. 厚いオファー

断る理由を列挙し、クロージング(個別の打ち消し + 感情の後押し)を設計します。

ゲート 5: 4 点セットが揃っているか。

## 11. コミュニケーションを設計する

まず MOA を定義します。

```text
見込み客が「今だ、これだ」と行動する瞬間、脳内に流れている決め手は〔決め手 1〜2 個〕である。
```

その後、LP / セールス導線を組みます。

1. FV / ビッグアイデア: 情報の触手を捕まえる入口
2. 共感: 欲求・痛みを再生する
3. 教育: 自社 USP が最高点になるモノサシを渡す
4. 約束: ベネフィットを特徴・効果・証拠で約束する
5. 交渉: オファーを YES にする(4 点セット + クロージング)
6. 提示: 理想のシーンを先取りさせる

3 つの Not(Not Read / Not Believe / Not Act)すべてに対策を置きます。

ゲート 6: 教育と約束の分離、3 つの Not、1.5 メートルを点検。

## 12. ファネルを描く

媒体をまたぐ全体動線として、次を描きます。

```text
リーチ → 見込み客獲得 → CRM
```

点検:

- どの媒体で、どんな姿勢の人に届くか(媒体価値 = 人数 × 時間 × 姿勢)
- どの接点でリスト化・初回購入へ進むか
- CRM で LTV をどう伸ばすか
- LTV ÷ CPA が 1 を超えるか
- 最もレバレッジの効く改善点はどこか

## 13. センターピンを決める

戦略全体を動かす最重要の一点を決めます。

候補:

- 製品品質
- 実績作り
- 特定の集客チャネル
- LP の教育パート
- 証拠作り
- コミュニティや紹介導線

出力文型:

```text
この戦略のセンターピンは〔一点〕である。ここが倒れると〔連鎖する成果〕が起きるため、ここにオーバーリソースを投下する。
```

## 14. 重要仮説を最速で検証する

重要仮説は、多くの場合、需要面にあります。

文型:

```text
この事業の成否を決める重要仮説は、〔狙う需要〕が〔十分な規模・強さ・購入意欲額〕で存在する、ということである。
```

検証手段:

- 顧客インタビュー
- テスト広告
- LP / 事前予約
- 小規模体験会
- 既存顧客へのオファー
- 手動販売

検証は、仮説の追認ではなく、否定兆候を探すために行います。

## 15. 撤退・変更条件を決める

仮説が崩れたら、小手先で延命しません。

事前に決めること:

- どの数値・反応なら継続するか
- どの数値・反応なら切り直すか
- どの違和感を正式な判断材料にするか
- 何を残し、何を捨てるか

## 16. セルフ監査する

出力前に、`knowledge/review-checklist.md` を回します。No が出た項目は直してから出力します。この工程は省略できません。

監査後、事業の確定事項・未検証仮説を `memory/` に書きます(`memory/README.md`)。

## 17. 社長向け提案にまとめる

提案は、事実整理で終わらせません。仮説とデータを添え、確信の構図で締めます。

提案文型:

```text
社長、この需要は大きく青く、我々の〔コアコンピタンス〕を使えば絶対に選ばれる理由があります。だから、〔狙う需要〕で No.1 を取りにいくべきです。そのために、まず〔センターピン〕へ集中し、〔重要仮説〕を最速で検証しましょう。
```
