# Memory

session 間で引き継ぐ事業ステートの置き場です。cmobank-cmo は単発回答ではなく、事業に伴走して仮説検証ループを回す存在です。前回までの暫定解と検証状況から再開するために、ここに状態を残します。

## 運用ルール

- 事業ごとに 1 ファイル: `memory/<事業スラッグ>.md`(例: `memory/cbd-sleep.md`)
- session の最初に読み、session の最後(セルフ監査後)に更新する
- 確定事項と未検証仮説を明確に分ける。検証で結果が出たら、仮説をログへ移して状態を更新する
- 日付は絶対表記(YYYY-MM-DD)で書く
- secret、token、個人情報は書かない

## ファイル形式

```markdown
# 〔事業名〕

## 現在地の一文分解(最終更新: YYYY-MM-DD)
今この事業は、〔どの需要〕に、〔どんな供給〕を当て、〔どんなコミュニケーション〕で取引を成立させている。

## ビジネスゴール
- ゴール / 期限 / 制約

## 確定事項(意思決定済み)
- 狙う需要: 〔需要〕(決定日: YYYY-MM-DD、根拠の要約)
- 商品コンセプト: 〔一文〕
- センターピン: 〔一点〕

## 未検証の重要仮説
- 〔仮説〕(検証方法 / 成功条件 / 失敗条件 / 状態: 未着手・検証中)

## 検証結果ログ
- YYYY-MM-DD: 〔何を検証し、何が分かり、どう判断したか〕

## 撤退・変更条件
- 継続: 〔条件〕 / 変更: 〔条件〕 / 撤退: 〔条件〕

## 次回への申し送り
- 〔次の session で最初にやること〕
```

## 何を書き、何を書かないか

書く:

- 意思決定(狙う需要の確定、コンセプトの採用、撤退判断)とその根拠の要約
- 検証の結果と、そこから更新した仮説
- 依頼者から得た一次情報(実績数値、顧客の声、制約)の要点

書かない:

- knowledge に書くべき長期参照の手順・原則
- 提案書の全文(成果物は project 側に残る。ここは状態だけ)
- 推測と事実を混ぜた記述(必ずラベルを分ける)
