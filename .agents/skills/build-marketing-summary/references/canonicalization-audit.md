# Canonicalization Audit

Workbenchの深い議論をCanonへ昇格するとき、文章量を減らしても判断を生む意味を失わないための監査手順。

## 目的

正本化は要約ではない。

検討過程、候補、重複を除きながら、現在の判断を成立させる次の要素を、適切な権威レベルへ移すことである。

- ユーザーが持つ欲望と需要
- 現在の断絶
- 解決原理
- 解決原理が有効だと考える基礎仮説
- 原因から変化までの因果
- ユーザーが得る客観的変化
- 約束しないこと、誤解させないこと
- 未確定のまま残す論点

## 昇格前の意味インベントリ

元となるWorkbenchを読み、文章を書く前に次を一行ずつ抽出する。

| 種類 | 抽出する問い |
|---|---|
| 欲望 | 最終的に何を実現したいのか |
| 需要 | 解決策として何を商品として欲しがるのか |
| 断絶 | 現在の代替では、なぜ実現できないのか |
| 基礎仮説 | なぜこの解決原理が有効だと考えるのか |
| 解決原理 | 何をどう変えるのか |
| 因果 | どの変化が次の何を生むのか |
| ユーザー変化 | BeforeからAfterへ何が変わるのか |
| 境界 | 何を約束せず、何を目的にしないのか |
| 保留 | まだ決めていないことは何か |

長い思想やストーリーは、結論だけでなく「なぜ必然的にその結論へ至るか」という因果も抽出する。

## 移送表

Canonを書く前に、意味インベントリの各項目について保存先を決める。

| 内容 | 主な保存先 |
|---|---|
| 一言一句を守る中心文言 | Verbatim Canon |
| 現在の需要、対象、価値、判断 | Decision Canon |
| 事業を導く構造的な基礎仮説 | 独立したDecision Canon、または明示的な節 |
| 決定理由、棄却案、変更経緯 | Decision Log |
| 根拠、生の声、調査 | Reference |
| 未確定候補 | Workbench |

一つの重要な意味に保存先がなければ、昇格を完了しない。

基礎仮説を短い説明へ押し込んで弱体化させない。後続の制作者が「なぜこの解決なのか」を判断するために必要なら、独立したDecision Canonへ分ける。

## 需要へ寄せる際の注意

ユーザー目線へ寄せることは、供給側の解決原理を消すことではない。

次を分離して保存する。

1. ユーザーが自然に欲しがる商品
2. ユーザーが得る変化
3. その変化を生む解決原理
4. 解決原理を支える基礎仮説
5. 供給カテゴリー

提供側の言葉を需要として売らない。同時に、需要の言葉だけを残して、競合と異なる解決原理や知性の仮説を失わない。

## 言葉の監査

論理が正しくても、次の表現は疑う。

- 「人間が本当に欲しいのは」のように、人間一般の欲望を断定する。
- 「最初に生まれた」「進化した」のように、説明に不要な起源を断定する。
- 「ユーザーが求めているのは」のように、読み手を外から分析する。
- 「理想の深さを理解する材料」のように、伝える内容ではなく分析上の役割を説明する。
- 「正しい」「本質的」「価値ある」のように、具体的な変化を示さない抽象語で済ませる。

修正方法:

- 観測できる状況、仕事、行動、変化を直接書く。
- 大きな起源説明ではなく、現在の因果に必要な範囲だけを書く。
- ユーザー向け文章では、読み手が自分の状況として読める主語にする。
- メタ説明を削り、その段落で本当に伝えたい判断を直接書く。

## 圧縮後の破壊テスト

完成前に、元のWorkbenchとCanonを並べ、次をYes / Noで判定する。

- [ ] 欲望と需要の違いが保存されている。
- [ ] 解決原理が、特徴の一覧へ縮小されていない。
- [ ] 基礎仮説の因果を、第三者が再現できる。
- [ ] ユーザーが得る変化が、管理の容易さなど小さな効果へ縮んでいない。
- [ ] 「なぜ競合ではなくこの解決なのか」の判断材料が残っている。
- [ ] 何を約束しないかが残っている。
- [ ] 未確定事項が確定事項へ混入していない。
- [ ] 正本だけを読んでも、元のWorkbenchと異なるカテゴリーのサービスに見えない。
- [ ] RAG、管理画面、効率化ツールなど、意図しない一般カテゴリーに見えないか反証した。
- [ ] 原文にある重要な一文が、移送表のどこにもない状態になっていない。

一つでもNoなら、文言を足す前に、Verbatim Canon、Decision Canon、基礎仮説、Referenceのどこへ置くべきかを再判断する。

## 人間確認

正本化案を提示するときは、短い文言だけを確認しない。

- 深い仮説で失われたものがないか
- 読み手に別カテゴリーのサービスとして見えないか
- 論理的には正しくても、本人の考え方として違和感のある断定がないか
- ユーザーの自然な言葉と、内部の解決原理が混ざっていないか

人間の「違和感」はコピー上の好みだけとして扱わない。需要、因果、抽象度、主語、カテゴリー認識のどこがずれたかまで戻って修正する。
